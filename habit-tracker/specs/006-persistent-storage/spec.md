# Feature Specification: データ永続化基盤の刷新

**Feature Branch**: `006-persistent-storage`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "006-persistent-storage"

## User Scenarios & Testing *(mandatory)*

本機能はテスト駆動で実装する。各ユーザーストーリーのAPI・ドメインロジック実装前にテストを
作成し、失敗することを確認したうえで実装を行う。フロントエンドUI（`public/`配下のVanilla
JS）はDOMテストツールを導入していないため自動テスト対象外とし、`quickstart.md`による手動
検証で品質を保証する。

### User Story 1 - 記録したデータが消えずに残り続ける (Priority: P1)

ユーザーは、習慣・チェックイン・目標・リマインダー設定を登録した後、アプリを閉じて
再度開いた場合や、アプリが再起動・再デプロイされた場合でも、そのデータが変わらず
残っていることを確認できる。

**Why this priority**: データが失われないことは習慣トラッカーとしての中核的価値であり、
これが成立しなければアプリ自体が実用に耐えない。これまでの永続化方式（サーバーの
実行環境内のみで有効なローカルファイル）では、常時アクセス可能な環境で運用した際に
データが失われる場合があったため、最優先で解消する。

**Independent Test**: 習慣を1件登録し、チェックインを1件記録したうえでアプリケーション
プロセスを再起動し、再起動後も習慣一覧・チェックイン履歴に登録した内容がそのまま
表示されることを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 習慣「読書」を登録し、本日分のチェックインを記録した状態、**When**
   アプリケーションプロセスが再起動（または再デプロイ）される、**Then** 再起動後も
   「読書」とそのチェックイン記録がそのまま表示される。
2. **Given** 目標やリマインダー表示設定を変更した状態、**When** 一定時間後に
   再度アプリを開く、**Then** 変更内容が保持されたまま表示される。
3. **Given** データが保存された状態、**When** 同じアプリケーションに複数回・複数の
   タイミングでアクセスする、**Then** 常に同一の最新データが参照できる（アクセスの
   たびにデータが初期化されない）。

---

### User Story 2 - 動作確認用のデータ操作が本番データに影響しない (Priority: P2)

ユーザー（開発者）は、動作確認や機能追加の検証作業を行っても、実際に使用している
本番環境のデータ（登録済みの習慣・チェックイン履歴等）が変化しないことを確認できる。

**Why this priority**: データ永続化の方式が「常時同じ保存先を使う」形に変わることで、
開発中の確認作業がそのまま本番データを書き換えてしまう新たなリスクが生じるため、
User Story 1に次いで優先度高く対応する。

**Independent Test**: 動作確認用に習慣を1件登録・削除したうえで、本番環境（実際に
利用しているデプロイ先）のデータを確認し、登録・削除の影響が一切反映されていない
ことを確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 開発環境で新しい習慣を登録した状態、**When** 本番環境のアプリを開く、
   **Then** 開発環境で登録した習慣は表示されない。
2. **Given** 本番環境に登録済みのデータが存在する状態、**When** 開発環境で動作確認の
   ための登録・編集・削除操作を行う、**Then** 本番環境のデータには一切変化が
   生じない。

---

### Edge Cases

- データ保存先への接続が一時的に確立できない場合はどうなるか？ → 操作は失敗として
  扱われ、ユーザーには分かりやすいエラーメッセージが表示される。中途半端な状態
  （一部のフィールドだけ保存される等）でデータが保存されてはならない。
- 過去に別方式（ローカルファイル）で保存されていたデータはどうなるか？ → 本機能では
  自動移行は行わない（Assumptions参照）。必要な記録があれば、新しい保存先に対して
  ユーザーが手動で再登録する。
- 開発環境・本番環境のどちらで操作しているか、画面上で判別できない場合に誤操作
  するリスクはないか？ → 本機能のスコープでは保存先の分離のみを対象とし、画面上の
  環境表示（バナー等）は別途検討事項とする。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、習慣・チェックイン・目標・リマインダー表示設定のすべての
  データを、アプリケーションプロセスの再起動や再デプロイをまたいでも失われない
  保存先に記録しなければならない。
- **FR-002**: システムは、同一環境（本番、または開発）に対する複数回・複数タイミングの
  アクセスに対して、常に一貫した最新のデータを返さなければならない。
- **FR-003**: システムは、`001-habit-management`〜`005-reminders`で定義された既存の
  全機能（習慣のCRUD、チェックイン記録、目標設定・進捗計算、レポート・
  ダッシュボード、リマインダー）を、保存先の変更後も従来と同じ振る舞いで提供し
  続けなければならない（機能面の後方互換性）。
- **FR-004**: システムは、開発環境で行われたデータの登録・編集・削除操作が、本番
  環境のデータに一切影響を与えない状態を維持しなければならない。
- **FR-005**: システムは、データ保存先への接続が一時的に失敗した場合、操作を
  中途半端な状態で完了させず、ユーザーに分かりやすいエラーメッセージを返さなければ
  ならない。
- **FR-006**: システムは、過去のローカルファイルによる保存データを新しい保存先へ
  自動的に移行する機能を提供する必要はない（Assumptions参照）。

### Key Entities

本機能は新しいデータの種類を追加しない。既存のエンティティ（習慣・チェックイン・
目標・リマインダー表示設定、`001`〜`005`で定義済み）の保存先・保存方式のみを
変更する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 登録した習慣・チェックイン・目標・リマインダー設定は、アプリケーション
  プロセスの再起動後も100%保持されている。
- **SC-002**: 開発環境での動作確認操作によって本番環境のデータが変化するケースは
  0件である。
- **SC-003**: データの保存・取得操作は、通常のネットワーク環境において3秒以内に
  完了する（`001`〜`005`で定めた基準を踏襲する）。
- **SC-004**: `001`〜`005`で定義された既存の受け入れシナリオ（Acceptance
  Scenarios）は、保存先の変更後も100%成立する（機能面の回帰が発生しない）。

## Assumptions

- 開発環境（ローカル）と本番環境（デプロイ先）は、同一のデータベースサービス内で
  互いに独立したデータベース（またはそれに相当する論理的な区画）を使用し、開発環境
  での操作が本番データに影響しないようにする。両者で完全に同一のデータ（同じ
  テーブル・同じ行）を共有することは想定しない。
- 過去にローカルファイルとして保存されていたデータ（動作確認のために登録した
  少量のテストデータ）は、本機能による自動移行の対象外とする。個人利用・少量
  データという前提のため、必要な記録があれば手動で再登録する（憲章原則V、
  シンプルさ）。
- 複数ユーザーによる同時アクセスや、大量データに対する性能要件は本フェーズの
  スコープ外とする（`001`〜`005`と同様、個人利用・単一ユーザー前提を継続する）。
- 保存先サービスの選定自体（既に憲章で確定済み）や、接続情報の具体的な管理方法は
  実装計画（`plan.md`）で扱う技術的な詳細であり、本仕様書では扱わない。
