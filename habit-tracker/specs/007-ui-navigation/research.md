# Research: 画面遷移UI（トップ・タブ・一覧・登録編集の分割）

本機能はTechnical Contextに`NEEDS CLARIFICATION`が残っていないため、リサーチ対象は
「フロントエンドの構造をどう再設計するか」という設計判断に絞られる。

## 1. 画面切り替えの実装方式

**Decision**: 単一`index.html`内に6つの`<section id="view-...">`をすべて配置し、
JavaScriptの`hidden`属性トグルで排他表示する（クライアントサイドルーター
ライブラリを使わない自前の最小実装）。

**Rationale**: `/speckit-clarify`前のユーザー確認で「1つのHTML内でJSによる画面
切り替え」が選定済み。既存`index.html`も`hidden`属性による表示/非表示切り替え
（例: `#reminder-list-empty`, `#habit-weekly-days`）を既に採用しており、同じ
パターンを画面単位に拡張するだけで実装できる。ブラウザURL・履歴と連動しない
（spec.md Assumptions）ため、`History API`や`hashchange`監視は不要で、`表示中の
画面名`を保持する変数と、対応する`<section>`の`hidden`切り替え関数だけで要件を
満たせる。

**Alternatives considered**:
- 画面ごとに別HTMLファイル（`habits.html`等）に分割 → `/speckit-clarify`前の
  ユーザー確認で不採用（ブラウザ履歴・URL直接アクセスが自然に使える利点は
  あるが、共通部分（タブメニュー等）の重複や状態共有の工夫が必要になり、本
  プロジェクトの規模には過剰）。
- クライアントサイドルーターライブラリ（例: Navigo等）導入 → 憲章の技術スタック
  制約「フロントエンド用フレームワークを導入しない」の趣旨（シンプルさ優先、
  原則V）に反するため不採用。単一ユーザー・6画面程度の規模ではライブラリ抜きで
  十分に実装できる。

## 2. 既存`public/js/habits.js`の分割方針

**Decision**: 画面（ビュー）単位でファイルを分割し、共通処理（API呼び出し・表示
フォーマット）は別モジュールに切り出す。具体的な構成は`plan.md`の
「Project Structure」参照（`app.js` / `api.js` / `format.js` / `views/*.js`）。

**Rationale**: 現状の`habits.js`（530行）は「習慣」「目標」「ダッシュボード」
「リマインダー」の処理が1ファイルに混在しており、画面分割の目的（迷わず目的の
機能にたどり着ける）と実装構造を一致させることで、今後の機能追加時にも該当
画面のファイルだけを見れば良い状態にする。`fetch`呼び出し（`loadHabits`,
`loadGoals`, `loadDashboard`, `loadReminders`等）は複数のビューから共通して
呼ばれる（例: 習慣のチェックインは習慣一覧・トップページ双方に影響する）ため、
`api.js`に集約し、各ビューはそこから必要な関数を呼び出す。

**Alternatives considered**:
- 分割せず`habits.js`のまま画面切り替えロジックだけ追加 → ファイルが画面数×
  平均行数でさらに肥大化し、「習慣一覧の見た目を直したいだけなのに目標や
  ダッシュボードのコードも読む必要がある」という、今回の画面分割が解消しようと
  している課題がフロントエンドのコード構造にも残ってしまうため不採用。
- ビルドツール（bundler）を導入してモジュールを結合 → 憲章制約（フレームワーク
  非導入・ビルド不要な構成の踏襲）に反するため不採用。ESモジュール
  （`<script type="module">`、既存`index.html`で採用済み）はビルドなしで
  ブラウザが直接複数ファイルを解決できるため、追加ツールは不要。

## 3. 画面間のデータ再取得・整合性

**Decision**: 画面切り替え時（タブ選択時・登録編集画面からの復帰時）に、対象
画面のデータを都度APIから再取得して再描画する（既存の`loadHabits()`等と同じ
パターンをビュー単位に適用）。

**Rationale**: 既存実装も、チェックイン・削除・登録等の操作後に`loadHabits()` /
`loadGoals()` / `loadDashboard()` / `loadReminders()`を都度呼び直す設計であり、
フロントエンド側にキャッシュや状態管理の仕組みを持たない。画面を分割しても
同じ方針（表示するたびに最新データを取得）を踏襲すれば、複数画面間のデータ
不整合（例: 習慣一覧で削除した習慣がホームのサマリーに残り続ける）を新たに
気にする必要がない。

**Alternatives considered**:
- 全画面のデータをアプリ起動時に一括取得し、以降はメモリ上のみで共有 → 画面
  遷移は速くなるが、複数画面をまたいだキャッシュ無効化（例: 目標を削除したら
  ダッシュボードのキャッシュも更新する）というシンプルさに反する複雑さが
  生じるため不採用（憲章原則V）。

## 4. トップページの簡易サマリー（習慣数・進行中の目標数）の算出

**Decision**: 習慣数は`GET /api/habits`のレスポンス件数、進行中の目標数は
`GET /api/goals`のレスポンスを取得し、フロントエンド側で`startDate <= 本日 <=
endDate`をフィルタしてカウントする。

**Rationale**: `/speckit-clarify`で「進行中の目標数」と確定したが、既存の
`GET /api/goals`エンドポイント（`003-goal-management`で実装済み）は全件を返す
契約のままであり、本機能はバックエンドAPIを変更しない方針（FR-014）のため、
絞り込みはフロントエンド側で行う。日付比較は既存`public/js/habits.js`の
`todayString()`（JST固定オフセット計算）をそのまま`format.js`に移設して再利用
する。

**Alternatives considered**:
- バックエンドに`GET /api/goals?status=in_progress`等のクエリパラメータを新設 →
  FR-014（既存APIの仕様・データモデルを変更しない）に反するため不採用。件数も
  少なく（個人利用規模）、フロントエンド側でのフィルタで性能上の問題もない。
