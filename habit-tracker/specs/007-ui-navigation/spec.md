# Feature Specification: 画面遷移UI（トップ・タブ・一覧・登録編集の分割）

**Feature Branch**: `007-ui-navigation`

**Created**: 2026-09-13

**Status**: Draft

**Input**: User description: "007-ui-navigation

習慣トラッカーのフロントエンド（public/）を、現在の単一index.html集約構成から、
画面遷移のある複数ビュー構成に分割する。1つのHTML内でJavaScriptによる画面切り替え
（SPA風、ページリロードなし）として実装する。

要望する画面構成:
- トップページ: リマインダー一覧 + 習慣数・目標数などの簡易サマリー表示
- タブメニュー: 「習慣」「目標」「ダッシュボード」を切り替え
- 「習慣」タブ → 習慣一覧画面
  - 新規登録ボタン → 習慣登録・編集画面へ遷移（登録またはキャンセルで一覧画面に戻る）
  - 各習慣の編集ボタン → 習慣登録・編集画面へ遷移（更新またはキャンセルで一覧画面に戻る）
- 「目標」タブ → 目標一覧画面
  - 新規登録ボタン → 目標登録・編集画面へ遷移（登録またはキャンセルで一覧画面に戻る）
  - 各目標の編集ボタン → 目標登録・編集画面へ遷移（更新またはキャンセルで一覧画面に戻る）
- 「ダッシュボード」タブ → ダッシュボード画面（既存のレポート機能）

バックエンドAPI・データモデルは変更しない。既存の001〜006で実装済みのAPI
（習慣CRUD・チェックイン・目標CRUD・レポート・リマインダー）をそのまま呼び出す
フロントエンドの構造変更のみ。"

## Clarifications

### Session 2026-09-13

- Q: タブメニューで「習慣」「目標」「ダッシュボード」のいずれかに切り替えた後、
  トップページ（リマインダー＋簡易サマリー）に戻る手段は必要か？ → A: 「ホーム」
  タブを追加し、タブメニューを「ホーム」「習慣」「目標」「ダッシュボード」の4項目
  とする。
- Q: トップページの簡易サマリーに表示する「目標数」はどちらを指すか？ → A:
  現在進行中（開始日≦今日≦終了日）の目標数のみをカウントする。

## User Scenarios & Testing *(mandatory)*

本機能はフロントエンド（`public/`配下のVanilla JS）の画面構成変更のみであり、
バックエンドAPI・データモデルの変更を伴わない。`001`〜`006`と同様、フロントエンドUIは
DOMテストツールを導入していないため自動テスト対象外とし、`quickstart.md`による手動
検証で各画面遷移・データ表示の正しさを保証する。

### User Story 1 - 迷わず目的の一覧にたどり着ける (Priority: P1)

ユーザーは、アプリを開いた直後のトップページで、今日やるべきこと（未実行の習慣）と
全体の状況（登録している習慣数・現在進行中の目標数）をひと目で把握でき、タブ
メニューから「ホーム」「習慣」「目標」「ダッシュボード」の各画面へ迷わず移動でき、
他の画面を見た後もいつでも「ホーム」タブからトップページに戻れる。

**Why this priority**: 現状は全機能が1画面に縦に並んでおり、目的の操作（例:
目標を1件追加したいだけ）のために無関係なセクションをスクロールして探す必要がある。
画面を分けて迷わずたどり着けるようにすることが、本機能の中核的な価値であり、
他のユーザーストーリー（一覧・登録編集画面）の土台になる。

**Independent Test**: 習慣を3件・進行中の目標を2件登録した状態でアプリを開き、
トップページに「習慣3件」「目標2件」の簡易サマリーとリマインダー一覧が表示され、
タブメニューの「習慣」「目標」「ダッシュボード」をそれぞれ押すと対応する画面に
切り替わり、続けて「ホーム」タブを押すと再びトップページに戻ることを確認するだけで、
単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 習慣・目標が複数登録されている状態、**When** ユーザーがアプリを開く、
   **Then** トップページにリマインダー一覧と、登録済みの習慣数・現在進行中の目標数の
   簡易サマリーが表示される。
2. **Given** トップページが表示されている状態、**When** ユーザーがタブメニューの
   「習慣」を選択する、**Then** ページ全体の再読み込みなしに習慣一覧画面へ切り替わる。
3. **Given** いずれかの一覧・登録編集画面が表示されている状態、**When** ユーザーが
   タブメニューの別の項目を選択する、**Then** 直前の画面の入力内容を保持したまま
   （またはUser Story 2/3の遷移ルールに従い）対応する画面へ切り替わる。
4. **Given** 「習慣」「目標」「ダッシュボード」のいずれかの画面が表示されている状態、
   **When** ユーザーがタブメニューの「ホーム」を選択する、**Then** 最新のリマインダー
   一覧・簡易サマリーを反映したトップページへ切り替わる。

### User Story 2 - 習慣を一覧から登録・編集する (Priority: P1)

ユーザーは、習慣一覧画面から新規登録画面・編集画面へ移動して習慣を登録・更新し、
完了またはキャンセルで自動的に一覧画面へ戻る。

**Why this priority**: 習慣管理（`001`）は本アプリの中核機能であり、一覧と登録編集を
画面単位で分離することがユーザーの要望の主眼であるため、User Story 1と同じ最優先度
とする。

**Independent Test**: 習慣一覧画面で「新規登録」ボタンを押して習慣を1件登録し、
自動的に一覧画面に戻ってその習慣が表示されること、次に一覧のその習慣の「編集」
ボタンを押して名前を変更し、更新後に一覧画面へ戻って変更が反映されていることを
確認するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 習慣一覧画面が表示されている状態、**When** ユーザーが「新規登録」
   ボタンを押す、**Then** 習慣登録・編集画面（新規モード）へ遷移する。
2. **Given** 習慣登録・編集画面（新規モード）で必要項目を入力した状態、**When**
   ユーザーが登録を実行する、**Then** 習慣が新規作成され、習慣一覧画面へ自動的に
   戻り、一覧に新しい習慣が反映されている。
3. **Given** 習慣登録・編集画面（新規モードまたは編集モード）が表示されている状態、
   **When** ユーザーがキャンセル操作を行う、**Then** 入力内容は破棄され、習慣一覧
   画面へ戻る（新規作成・更新は行われない）。
4. **Given** 習慣一覧画面のいずれかの行で「編集」ボタンを押した状態、**When**
   習慣登録・編集画面が開く、**Then** その習慣の現在の値がフォームに反映された
   編集モードで表示される。
5. **Given** 習慣登録・編集画面（編集モード）で値を変更した状態、**When** ユーザーが
   更新を実行する、**Then** 対象の習慣が更新され、習慣一覧画面へ自動的に戻り、
   一覧に変更後の内容が反映されている。

### User Story 3 - 目標を一覧から登録・編集する (Priority: P2)

ユーザーは、目標一覧画面から新規登録画面・編集画面へ移動して目標を登録・更新し、
完了またはキャンセルで自動的に一覧画面へ戻る。

**Why this priority**: 目標管理（`003`）はUser Story 2（習慣）と同一パターンの画面
分割であり、実装上はUser Story 2で確立した遷移の仕組みを踏襲できるため、優先度を
1段階下げても独立した価値を提供できる。

**Independent Test**: 目標一覧画面で「新規登録」ボタンを押して目標を1件設定し、
自動的に一覧画面に戻ってその目標が表示されること、一覧のその目標の「編集」ボタンを
押して目標回数を変更し、更新後に一覧画面へ戻って変更が反映されていることを確認
するだけで、単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 目標一覧画面が表示されている状態、**When** ユーザーが「新規登録」
   ボタンを押す、**Then** 目標登録・編集画面（新規モード）へ遷移する。
2. **Given** 目標登録・編集画面（新規モード）で必要項目を入力した状態、**When**
   ユーザーが登録を実行する、**Then** 目標が新規作成され、目標一覧画面へ自動的に
   戻り、一覧に新しい目標が反映されている。
3. **Given** 目標登録・編集画面（新規モードまたは編集モード）が表示されている状態、
   **When** ユーザーがキャンセル操作を行う、**Then** 入力内容は破棄され、目標一覧
   画面へ戻る。
4. **Given** 目標一覧画面のいずれかの行で「編集」ボタンを押した状態、**When**
   目標登録・編集画面が開く、**Then** その目標の現在の値がフォームに反映された
   編集モードで表示される。
5. **Given** 目標登録・編集画面（編集モード）で値を変更した状態、**When** ユーザーが
   更新を実行する、**Then** 対象の目標が更新され、目標一覧画面へ自動的に戻り、
   一覧に変更後の内容が反映されている。

### User Story 4 - タブからダッシュボードを確認する (Priority: P3)

ユーザーは、タブメニューから既存のダッシュボード（`004`で実装済みのレポート機能）を
専用の画面として表示できる。

**Why this priority**: ダッシュボードは既存機能をそのまま独立した画面に配置する
だけであり、他のユーザーストーリーが完成していれば最後に対応しても価値の提供に
支障がないため、優先度3とする。

**Independent Test**: タブメニューの「ダッシュボード」を選択し、既存の実施率・
最長ストリーク・目標の達成状況が引き続き正しく表示されることを確認するだけで、
単独で価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 習慣・チェックイン・目標が登録されている状態、**When** ユーザーが
   タブメニューの「ダッシュボード」を選択する、**Then** `004-reports-dashboard`
   で実装済みの内容（習慣ごと・カテゴリ別の実施率、目標の振り返り）がそのまま
   表示される。

---

### Edge Cases

- 習慣・目標が1件も登録されていない状態でトップページを開いた場合はどうなるか？
  → 簡易サマリーは「習慣0件」「目標0件」と表示し、リマインダー一覧は
  `005-reminders`の既存仕様通り「今日の習慣はすべて実行済みです」を表示する
  （エラーにはしない）。
- 目標は登録されているが、すべて開始日が未来または終了日が過去（進行中の目標が
  1件もない）の場合はどうなるか？ → 簡易サマリーの「目標数」は0件と表示する
  （進行中の目標のみをカウントする定義に従う）。
- 登録・編集画面で入力途中にタブメニューから別のタブへ移動した場合はどうなるか？
  → 入力内容は破棄され、遷移先の一覧画面が表示される（明示的な保存操作を
  伴わない離脱は、キャンセル操作と同様に扱う。ブラウザの「戻る」相当の確認
  ダイアログ等は本フェーズのスコープ外とする）。
- 一覧画面の「編集」ボタンを押した後、対象のデータが他の操作（例: 別タブでの
  削除）で既に存在しなくなっていた場合はどうなるか？ → 既存API（`001`/`003`）の
  404エラー処理に従い、エラーメッセージを表示した上で一覧画面に留まる。
- 習慣一覧画面のカテゴリ絞り込み（`001`で実装済み）は、画面を離れて戻ってきた際に
  維持されるか？ → 本フェーズでは維持しない（一覧画面へ戻るたびに絞り込み条件は
  初期状態に戻る、既存の単一画面時代の挙動からの変更点として許容する）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、アプリを開いた際にトップページとして、本日のリマインダー
  一覧（`005-reminders`のFR-001〜FR-003を踏襲）と、登録済み習慣数・現在進行中
  （開始日≦本日≦終了日）の目標数の簡易サマリーを表示しなければならない。
- **FR-002**: システムは、常時表示されるタブメニューから「ホーム」「習慣」「目標」
  「ダッシュボード」の4画面を、ページ全体の再読み込みなしに切り替えられなければ
  ならない。「ホーム」タブは常にトップページ（FR-001）を表示する。
- **FR-003**: 「習慣」タブは、既存の習慣一覧（`001`のFR、カテゴリ絞り込みを含む）を
  表示する専用画面としなければならない。
- **FR-004**: 習慣一覧画面は、新規登録操作と、一覧の各項目に対する編集操作を提供
  しなければならない。
- **FR-005**: システムは、習慣の新規登録・編集を、一覧画面とは別の習慣登録・編集
  画面として提供しなければならない。
- **FR-006**: 習慣登録・編集画面は、登録（または更新）操作の完了時、および
  キャンセル操作時のいずれにおいても、習慣一覧画面へ遷移しなければならない。
- **FR-007**: 習慣登録・編集画面を編集モードで開いた場合、対象の習慣の現在の値
  （名前・頻度・曜日・カテゴリ・リマインダー表示設定）がフォームに初期値として
  反映されていなければならない。
- **FR-008**: 「目標」タブは、既存の目標一覧（`003`のFR）を表示する専用画面と
  しなければならない。
- **FR-009**: 目標一覧画面は、新規登録操作と、一覧の各項目に対する編集操作を提供
  しなければならない。
- **FR-010**: システムは、目標の新規登録・編集を、一覧画面とは別の目標登録・編集
  画面として提供しなければならない。
- **FR-011**: 目標登録・編集画面は、登録（または更新）操作の完了時、および
  キャンセル操作時のいずれにおいても、目標一覧画面へ遷移しなければならない。
- **FR-012**: 目標登録・編集画面を編集モードで開いた場合、対象の目標の現在の値
  （対象習慣・開始日・終了日・目標回数）がフォームに初期値として反映されて
  いなければならない。
- **FR-013**: 「ダッシュボード」タブは、既存の`004-reports-dashboard`の表示内容
  （習慣ごと・カテゴリ別の実施率、目標の振り返り）をそのまま表示しなければ
  ならない。
- **FR-014**: システムは、既存の習慣CRUD・チェックイン・目標CRUD・レポート・
  リマインダーの各API（`001`〜`006`で実装済み）の仕様・データモデルを変更しては
  ならない。本機能はフロントエンドの画面構成変更のみとする。
- **FR-015**: システムは、リマインダー一覧からのその場でのチェックイン
  （`005-reminders`のUser Story 2）を、トップページ上で引き続き提供しなければ
  ならない。

### Key Entities

本機能はデータモデルを追加・変更しない。既存の習慣（Habit）・チェックイン
（CheckIn）・目標（Goal）を、画面（トップページ／習慣一覧／習慣登録・編集／
目標一覧／目標登録・編集／ダッシュボード）という新しい表示上の単位に再構成する。

- **画面（View）**: 永続化されるエンティティではなく、フロントエンド上でユーザーに
  提示される表示単位（トップページ・習慣一覧・習慣登録編集・目標一覧・目標登録
  編集・ダッシュボードの6種類）。ユーザーの操作に応じて排他的に1つが表示される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーはアプリを開いてから3秒以内（クリック1回以内）に、目的の
  画面（習慣一覧・目標一覧・ダッシュボードのいずれか）に到達できる。
- **SC-002**: 画面の切り替えはページ全体の再読み込みを伴わず、切り替え後も
  それまでの他の画面の状態（例: リマインダー一覧の内容）が失われない。
- **SC-003**: 習慣・目標の新規登録および編集は、開始から完了（一覧画面への復帰）
  まで、既存の単一画面構成と比べて操作手順（クリック数）が増加しない。
- **SC-004**: 100%のケースで、登録・更新・キャンセルのいずれの操作後も、
  ユーザーは意図した一覧画面に戻り、迷子（存在しない画面や空白画面の表示）に
  ならない。

## Assumptions

- 画面遷移はブラウザのURL（アドレスバー）やブラウザ履歴（戻る/進むボタン）とは
  連動させない、アプリ内部の状態のみによる画面切り替えとする。ブラウザの戻る
  ボタンでの画面遷移や、特定画面への直接URLアクセス（ディープリンク）は本フェーズ
  のスコープ外とする（憲章原則V、シンプルさ）。
- タブメニューは常時（どの画面を表示中でも）画面上部などに表示され、いつでも
  他のタブへ切り替えられるものとする。
- 画面遷移アニメーションやトランジション効果の有無は本フェーズで規定せず、
  実装時の裁量とする。
- 本機能はフロントエンド（`public/`配下）のみの変更であり、`001`〜`006`で実装済みの
  バックエンドAPI（`src/routes/`・`src/repositories/`・`src/domain/`）およびVercel
  Postgres（`006-persistent-storage`）のデータモデルには一切変更を加えない。
- 既存の`public/js/habits.js`に集約された処理は、画面単位（トップページ・一覧・
  登録編集・ダッシュボード）で複数のモジュールに分割してよいものとする（具体的な
  ファイル分割方針は`/speckit-plan`で決定する）。
