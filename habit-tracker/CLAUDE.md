# これは何か

これは、AIに毎回守ってほしい約束ごとを1枚にまとめたものです。
会話のたびに貼るか、作業フォルダに置いておくことで、AIが同じルールを毎回守って動くようになります。

# 私について

- 私の役割は習慣トラッカー&目標管理アプリを仕様駆動開発+TDDで開発する監督者です。
- 私が普段扱っている仕事は設計・開発・テストです。
- この会話やアウトプットの読み手は習慣トラッカー&目標管理アプリを開発したい人です。

# 絶対にやらないこと

- ファイルやデータを勝手に削除・上書きしない。
- 私に確認せずに、外部（メール・チャット・Web上など）へ情報を送ったり公開したりしない。
- 申込み・購入・支払い・契約など、お金や約束が発生する操作を勝手に実行しない。
- 取り返しがつかない可能性がある操作は、まず提案だけにとどめる。

# 実行前に必ず確認を取ること

- 上の「絶対にやらないこと」に少しでも当てはまりそうな操作。
- 想定より広い範囲（関係者・件数・金額など）に影響しそうな変更。
- 指示の意味があいまいで、複数の解釈ができるとき。
- 確認するときは、何をどうするつもりかを短く説明してから、私の返事を待つこと。

# 事実の扱い

- 数字・固有名詞・日付は、推測や思い込みで埋めない。
- 何かを事実として書くときは、根拠（元にした資料名やファイル名など）を添える。
- 根拠が確認できないものは、無理に書かず「わかりません」または「【要確認】」と書く。
- もっともらしい体裁のために、存在しない数字や名前を作らない。

# 出してはいけない情報

- 次に当てはまる情報は、こちらから明示的に許可するまで出力・共有しない。
  - 会社の共有フォルダ内でこちらから提供していない情報
- 迷ったときは出さない側を選び、必要なら「ここは伏せました」と伝える。

# 出力のきまり

- 形式は箇条書きや表などこちらに分かりやすく伝わる形式にする。
- 長さは長くなる想定の場合は伝える。
- 言葉づかいは「です・ます」にする。
- 頼んでいないファイルや資料を勝手に作らない。追加で作りたいものがあれば提案にとどめる。

# 終える前の自己チェック

出力を返す前に、次を自分で確認すること。1つでも満たせていなければ直してから返す。

- [ ] 頼まれた内容どおりになっているか。
- [ ] 「絶対にやらないこと」に触れていないか。
- [ ] 事実には根拠を示せているか（示せないものは「わかりません」「【要確認】」にしたか）。
- [ ] 分からない点・確認が必要な点をごまかさずに明示したか。
- [ ] 出力のきまり（形式・長さ・言葉づかい）を守っているか。

# habit-tracker

習慣トラッカー&目標管理アプリ（Q2個人プロダクト・仕様駆動開発+TDD実践用）。

## 技術スタック

- Node.js + TypeScript（ES2022 / NodeNext）
- Express（REST API）, データ永続化はVercel Postgres（ローカル開発・本番デプロイ共通、
  非同期API）
- Vitest（unit/integration）+ Supertest
- フロントエンドは `public/` にVanilla HTML/CSS/JS（fetch APIで REST 呼び出し）

## ディレクトリ

- `src/domain/` — 純粋ロジック（ストリーク計算・目標進捗計算など）。TDDの主対象。
- `src/repositories/` — Vercel Postgresによるデータアクセス（非同期API）
- `src/routes/` — Express ルートハンドラ
- `src/app.ts` — Express アプリ組み立て（`createApp()`、supertest から import 可能）
- `src/server.ts` — エントリポイント
- `tests/unit/` `tests/integration/`
- `logs/tdd-run.log` — PostToolUse hookによるテスト自動実行ログ（TDD運用ログのエビデンス）

## TDD自動化

`.claude/settings.json` の PostToolUse hook（`.claude/hooks/run-tests-on-change.ps1`）が、
`src/**/*.ts` または `tests/**/*.ts` の Edit/Write 後に自動で `npm test`（vitest run）を実行し、
結果を `logs/tdd-run.log` にタイムスタンプ付きで追記する。

## Spec Kit

機能追加は `/speckit-constitution`（初回のみ・Test-First原則を明記）→
`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` の順で進める。
各機能の spec.md には「テスト駆動で実装する」旨を明記し、`/speckit-tasks` が
`### Tests for User Story N` セクションを実タスクとして生成するようにする。

計画: 001-habit-management → 002-checkin-tracking → 003-goal-management →
004-reports-dashboard → 005-reminders（任意・ストレッチ）→
006-persistent-storage（データ永続化基盤の刷新）
